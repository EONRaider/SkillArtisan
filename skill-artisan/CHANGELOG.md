# Changelog

All notable changes to SkillArtisan are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [Semantic Versioning](https://semver.org/), interpreted for this project as:

- **Major version bump (1.0.0 → 2.0.0)** marks a v-stage boundary, not just a breaking change — v1 → v2 is the deliberate release split (see the master spec's "Build Stages → Plugin Files → Release Scope"), not an accident of semver discipline.
- **Minor version** for new capability within a stage that doesn't break existing usage (e.g. adding cross-agent evaluation as an opt-in mode within v1).
- **Patch version** for fixes — corrected patterns, tightened validation, documentation accuracy.

## [Unreleased]

### Deferred, not forgotten
- **Multi-model verification scope, reduced from the literal smoke preset.** `--preset smoke` nominally means 5 runs per configuration, with/without-skill both. Running the full 5×2×3-model matrix (30 runs per eval, 180 total) was disproportionate to what "quick capability check" should cost, so the actual run below used 1 rep, with-skill only, per eval per model (18 runs). This answers the real question ("does `creating-skills` perform reliably across model sizes") without re-deriving a with/without delta per model, which the checklist item doesn't ask for. Noted here so a future full-rep run isn't assumed redundant.
- **Best-in-Market Scorecard full run** (master spec's "Best-in-Market Scorecard" section, companion prompt's "The Best-in-Market Scorecard (full run)"). Both source documents gate this explicitly behind "if asked to run it" — it requires building a 12-20 skill benchmark corpus, cloning and running `daymade/claude-code-skills` and `tripleyak/SkillForge` as live comparison arms alongside Anthropic's shipped `skill-creator`, and dozens of real `claude -p` with/without-skill benchmark runs per arm. Not run yet; nobody asked for it yet, and the master spec is explicit that "best in market" must not be claimed anywhere until it has been. Axis 1 (checklist compliance) can now be scored against the *full* Gap Table rather than the v1-scoped subset, since v2 is shipped — that's the one thing `2.0.0` changed about the scorecard's own preconditions.
- **Fresh-session confirmation of `agents/*.md` subagent invocability post-install.** `2.1.0` confirmed a local install doesn't refresh the *current* session's subagent-type registry; a session started fresh *after* install is expected to pick the plugin's agents up (the same mechanism verified working in `[1.0.0]`), but that specific half wasn't independently re-tested inside this session's own tooling — noted so it isn't silently assumed confirmed twice over.

## [2.2.3] - 2026-08-18

A fourth real bug found in row 15's ported eval engine, this time by deliberate hardening rather than incidental discovery during a benchmark run — triggered by investigating why Axis 2 trigger-accuracy scoring (`axis2_trigger_scorer.py`) had `--num-workers` capped at 1.

### Fixed
- **`description_optimizer.py`'s `run_single_query()` published and tore down its synthetic per-query skill directory non-atomically** (`mkdir()` then a separate `write_text()` to publish; `unlink()` then a separate `rmdir()` to tear down), both against the same shared `.claude/skills/` directory every concurrent worker scans at startup. Between the two calls in each pair there's a real window where a concurrent scan can observe a broken entry — a directory with no `SKILL.md` yet, or (for teardown) one that's already been emptied but not yet removed. Fixed by building each entry in a hidden staging directory and publishing/removing it with a single `os.rename()`, which is atomic on the same filesystem: a directory listing during either operation now only ever sees the complete entry or nothing, never a partial one. Verified with a dedicated concurrency stress test (no LLM calls — pure filesystem race, `race_stress_test.py` under scratch) that reproduces the mechanism directly: with a deliberate delay forced into the vulnerable window, the old code exposed a broken entry in ~99% of concurrent scans; the fix brought that to 0%.
- **Correction to prior understanding, not a fix**: this atomic-write race is real and worth fixing, but it turned out not to be the (or the whole) cause of the `--num-workers 4` → 0% trigger-detection collapse originally documented in `axis2_trigger_scorer.py`'s `--num-workers` help text. Live validation after the fix (`debugging-network-issues`, `--num-workers 4` vs. the known-good `--num-workers 1` baseline of 14/16) still dropped to 10/16, with every failure showing 0 triggers across all runs and the log showing every query timing out at 180s — including ones that "passed" only because a timeout reads as not-triggered, which happens to match a should-not-trigger query's correct answer. Sequential runs show the same 100%-timed-out log pattern but sane, varied pass rates, because `run_single_query` correctly latches its `triggered` result from a mid-stream tool-use event well before the session's later work (actually reading/using the skill) blows through the timeout — that part is normal. What's different at 4 workers is that several queries never got that far at all: the tool-call decision itself didn't happen in time. That points to raw resource contention (four concurrent `claude -p` processes competing for CPU/network/API throughput on one machine) as the dominant remaining bottleneck, not a filesystem race — so `--num-workers 1` stays the safe default until that's separately investigated. The fix above is real and shipped regardless; it just isn't the unlock it looked like it might be.
- **Confirmed present in `skill-creator`'s own shipped `run_eval.py`, and worse**: the identical `mkdir()`-then-`write_text()` pattern exists there too (lines 57/68), with more code running between the two calls than SkillArtisan's version had even before this fix — a wider vulnerable window, still unfixed upstream as of this check. See the master spec's Confidence Notes for the running tally of verified skill-creator defects.

## [2.2.2] - 2026-08-18

Three real bugs found and fixed in row 15's eval/description-optimization engine — `description_optimizer.py` and `eval_loop.py` are direct ports of `skill-creator`'s own `run_eval.py`/`run_loop.py`/`improve_description.py`/`generate_report.py` and `aggregate_benchmark.py` respectively (see the master spec's Confidence Notes); `security_scan.py` is `daymade/claude-code-skills`' architecture, not a `skill-creator` port. All three were caught during real production use: authoring and eval-testing 13 new corpus skills through `creating-skills` end-to-end (single-arm regression testing, see the master spec's Best-in-Market Scorecard correction), not by inspection or a dry run.

### Fixed
- **`description_optimizer.py`'s `run_single_query()` returned prematurely on the first non-Skill/Read tool call or first assistant message**, causing false-negative trigger detection instead of watching the full conversation through to the `result` event. Removed the premature `return` statements; the function now only returns from inside the `result`-event branch.
- **`description_optimizer.py`'s default 60-second timeout was too short for real `claude -p` calls**, which observed 2-3+ minutes in practice. Raised to 180s, with a stderr warning on timeout added (the function's plain-bool return type couldn't be changed without breaking other callers, so the timeout itself isn't distinguishable from a genuine negative result to callers — the warning is the mitigation).
- **`eval_loop.py`'s `load_run_results()` crashed on an explicit JSON `null`** in timing/metrics fields (as opposed to a missing key) — a grader legitimately unable to recover timing data writes explicit `null` rather than omitting the key, and `calculate_stats` crashed on `sum([..., None, ...])`. Fixed via a `.get(key) or default` pattern throughout.
- **`security_scan.py --json` mode leaked human-readable text onto stdout after the JSON payload** on clean scans, breaking anything parsing the output as JSON (11 of 12 `--json` scans in the regression run failed to parse for this reason before the fix). That text now routes to stderr when `--json` is set.

## [2.2.1] - 2026-08-16

`pr-execute --execute`'s first live end-to-end test, against a disposable repo (`EONRaider/skillartisan-pr-execute-test`) created specifically for this, with explicit sign-off immediately before the live invocation per the plan. Found and fixed one real bug along the way.

### Fixed
- **`find_existing_pr`'s idempotency check silently found nothing for a same-repo (direct-push, no-fork) target.** `gh pr list --head` takes a bare branch name for a PR whose head is in the same repo, but requires `owner:branch` syntax specifically for a cross-repo (forked) PR — the function used `owner:branch` unconditionally. Surfaced live: after the first `--execute` run genuinely opened a real PR (`.../pull/1`, correctly additive-only — `SKILL.md` +4/-0, `evals/evals.json` +24/-0, zero deletions), a second run against the same skill fell through the idempotency check entirely and attempted a real push, which then failed on an unrelated non-fast-forward error rather than being caught by the check that exists specifically to prevent that attempt. `find_existing_pr` now takes the same `direct_push` signal `ensure_fork` already computes, and picks the correct `--head` format accordingly. Verified: a third run correctly short-circuits to the existing PR's URL, exit 0, no duplicate PR, working tree and current branch both left untouched (confirmed via `gh pr list` and `git status`/`git branch` before and after).
- Confirms the additive-only invariant holds in a real committed diff, not just the dry-run preview: the actual merged file list for `.../pull/1` shows zero deletions.

The disposable test repo and its one open PR are left in place — nothing about this repo needs preserving, but deleting a repository is exactly the class of irreversible action this project's own safety model reserves for the user's own explicit action, not something to do unprompted even for scratch material.

## [2.2.0] - 2026-08-16

Closes row 32's real-execution half. `audit.py pr-plan` has always been plan-only; this adds the actual fork/branch/commit/push/PR mechanics as a separate, explicitly-gated path, per the master spec's requirement that opening a PR against a repo this plugin doesn't own needs explicit human confirmation every time, not once per skill.

### Added
- **`scripts/pr_execute.py`** (row 32, execution half): a new, separate script (not folded into `audit.py`, per the `scripts/` discipline — one script computes reports, this one performs side effects) that takes a local clone with an additive fix already applied as uncommitted changes, and branches/commits/pushes/opens a PR against the stated upstream repo. Deliberately does not author fixes itself — content authoring stays high-freedom, judgment-heavy work done by the orchestrator with normal Read/Edit/Write, the same as any other real fix; this script is scoped to the low-freedom, exact-script mechanics around an already-made change.
  - `--dry-run`: computes and prints the branch name, diff summary, and PR preview with zero git/gh mutation. This is the default-safe mode and was exhaustively tested (see Deferred, above, for what wasn't).
  - `--execute`: performs the real fork/branch/commit/push/PR sequence. No prompt of its own and no auto-confirm flag — the confirmation gate is structural, one layer up in the orchestrator's chat turn, exactly as `creating-skills/SKILL.md` subsection 6 already required before this shipped.
  - **Hard invariant**: refuses (exit 4) if the change set includes any file deletion or rename, checked mechanically against `git status --porcelain` — additive-only is enforced, not left to discretion.
  - **Idempotent**: a deterministic (non-time-stamped) branch name per skill, checked via `gh pr list` before creating anything — a rerun against a skill with an already-open PR returns that PR's URL rather than opening a duplicate.
  - Distinct exit codes throughout (nothing-to-contribute, non-additive refusal, `gh` not installed/not authenticated, fork/push/PR-creation failure, success), mirroring `security_scan.py`'s precedent of distinguishing "the tool itself couldn't run" from "a real problem was found."
- **`scripts/audit.py pr-execute`**: thin wrapper subcommand delegating to `pr_execute.py`, so `audit.py` stays the single entry point for every audit-related subcommand while the git/gh logic lives in its own tiny, separately-runnable module (same reuse pattern as `validate.py`/`security_scan.py` already used by `report`/`bulk`).
- **`creating-skills/SKILL.md`**: subsection 6 rewritten to describe the two-step plan-then-execute flow, and `compatibility` frontmatter now lists `gh` (authenticated) as a requirement for the execution path only — everything else in the skill works without it.

### Fixed
- `audit.py pr-plan`'s and `SKILL.md` subsection 6's prose both said "never forks, commits, or opens anything" in the present tense — true when written, false the moment real execution existed elsewhere. Both revised to describe the actual current split between the plan-only command and the separate, execution-capable one.

## [2.1.0] - 2026-08-16

Closes three of the five `[Unreleased]` items from `2.0.1`: `creating-skills` now has its own eval suite, it's been verified across all three model sizes, and the `agents/*.md` subagent-invocability gap has been directly tested rather than left as an open question. All three real findings below were caught by actually running the thing, not by writing it and assuming it was right.

### Added
- **`creating-skills/evals/evals.json`** (row: `evals-present`, previously FAIL, now PASS — `audit.py report` confirms 16/17, up from 15/17). Six scenarios exercising the Decision Gate directly: a CLAUDE.md-shaped misroute, a ≥80% dedup match, a 50-79% dedup match with an inline-vs-fork call, a genuine compose case, a fork-vs-inline worked pair, and a security-gate packaging refusal. Verified concrete enough to actually grade — not just plausible-looking prose — via a real subagent run against eval 1, scored 3/3 PASS with cited evidence.
- **Multi-model verification of `creating-skills`**, real results, not a claim it "should work": with-skill runs across Haiku, Sonnet, and Opus as executor (1 rep per eval per model, 18 runs total — see the scope note in `[Unreleased]` above for why this isn't the full 5-rep preset). `eval_loop.py aggregate`: **Haiku 83.3%, Sonnet 100%, Opus 100%.** Haiku failed eval 4 (the compose case) specifically — it never searched beyond the default project-local path, never evaluated a real candidate skill's content, and routed to a "hook-based automation" category that doesn't exist anywhere in `creating-skills`' own Decision Gate table, rather than working within the documented gate. Sonnet and Opus both searched the marketplace, correctly identified `claude-md-improver` as a real match, and correctly read past two superficially-plausible candidates (`session-report`, `receipts`) to reject them on their actual content. Opus went further still, independently flagging that the Decision Gate table itself has no row for hooks at all (see Fixed, below) and that eval 5's codebase-audit half has a genuine compose signal with this session's own `code-review`/`security-review`/`simplify` skills.
- **`creating-skills/SKILL.md`'s "Testing and evaluating" section** documents the Task-tool `model` parameter as the actual mechanism for pinning an executor's model during a smoke pass — nothing in this plugin's own scripts does this (`description_optimizer.py --model` only pins `claude -p` subprocess calls, not Task-tool subagent spawns), so it was undocumented until now.
- **The `agents/*.md` subagent-invocability gap, directly tested rather than assumed.** Added a local test marketplace, installed `skill-artisan` from it (`claude plugin marketplace add`/`claude plugin install`, confirmed enabled via `claude plugin list`), then tried `Task(subagent_type: "grader"/"comparator"/"analyzer")` in the same session — all three came back `Agent type '...' not found`. Confirms the registry is fixed at session start and a local install mid-session doesn't refresh it; a fresh session started after install is expected to pick the plugin's agents up (the same discovery mechanism already verified working in `[1.0.0]`), but that half wasn't independently re-confirmed inside this session's own tooling. Documented both paths — installed (`Task(subagent_type: ...)` direct) vs. repo-context (the proven manual fallback, follow each agent `.md`'s process by hand) — in `SKILL.md`'s "Testing and evaluating" section and `README.md`'s Install section, so this isn't a silent trap for the next person developing the plugin itself.

### Fixed
- **`creating-skills/SKILL.md`'s Decision Gate had no routing row for hooks.** Found by Opus's own eval 4 response, independently, while working the actual eval: a request for deterministic per-session automation ("every time I finish a work session") has no home in the gate's routing table — CLAUDE.md, AGENTS.md, MCP, subagent, DESIGN.md, and plugin are all there, but a lifecycle-hook case isn't, even though hooks are real, common automation requests this skill needs to route correctly. Added a row distinguishing "always-true context" (CLAUDE.md/AGENTS.md) from "deterministic action tied to a lifecycle event" (a `settings.json` hook, configured via `update-config`) — the exact distinction Opus had to reconstruct from first principles because the table didn't state it.
- **`creating-skills/evals/evals.json`'s eval 4 named the wrong skill as a compose candidate.** Written from the skill's *name* (`session-report`) without reading its actual content — it's a token/cache/cost usage report from Claude Code transcripts, not a narrative of what changed in a session. Sonnet's and Opus's eval 4 responses both caught this by actually reading the candidate's SKILL.md, which meant the original eval would have failed a *correct* response and rewarded an incorrect one that happened not to name the mismatched skill either. Rewrote the eval's `expected_output`/`expectations` to test the underlying competency (read real candidate content, don't assume from name) rather than hardcoding a specific pair of skill names that turned out to be wrong.

## [2.0.1] - 2026-08-16

Four fixes, all found the same way — by actually running `scripts/audit.py`, `validate.py`, and `eval_loop.py` against real, external data (Anthropic's shipped `skill-creator`, every plugin in the real local marketplace, and a live end-to-end regression-benchmark run) rather than trusting them by inspection. No Gap Table rows affected; these are correctness fixes to existing `2.0.0` behavior, not new capability.

### Fixed
- **`scripts/_common.py`'s `find_skill_dirs` missed the real Claude Code plugin layout.** `audit.py bulk` against the actual installed marketplace (`~/.claude/plugins/marketplaces/claude-plugins-official/plugins`) returned "No skills found" despite 25 real `SKILL.md` files existing there — the function's two-level glob assumed `<plugin>/<skill>/SKILL.md`, but every real installed plugin uses `<plugin>/skills/<skill>/SKILL.md` instead. Added an explicit `*/skills/*/SKILL.md` glob for this shape. Verified: `audit.py bulk` now finds and audits all 25 real skills; `dedup_search.py`, which shares this function, is unaffected on its default paths and now also finds candidates when pointed at the marketplace.
- **`scripts/_common.py`'s frontmatter parsers silently dropped a description with no block-scalar marker.** `audit.py report` against a real installed skill (`math-olympiad`) came back `REBUILD` — its 704-char description read as 0 chars. The description was written as a bare `description:` with the actual quoted value starting on the next line (valid YAML: a plain/quoted scalar can wrap across lines with no `>`/`|` marker at all), a shape neither `parse_skill_md` nor `parse_frontmatter_raw` handled — they only followed a continuation after an explicit block-scalar marker. Factored both parsers onto one shared `_parse_frontmatter_lines` helper that now handles same-line values, block-scalar markers, and bare-multiline values explicitly (the third case's continuation gets its wrapping quotes stripped as syntax; the block-scalar case's does not, since quotes are literal content there). Verified: the false `REBUILD` flips to the correct `upgrade-in-place`; full regression sweep across `skill-creator`, `creating-skills`, `drafting-changelog-entries`, and the dummy test skills showed no change elsewhere.
- **`scripts/validate.py`'s stripped-copy reconstruction could produce invalid YAML.** Synthetic testing of the four YAML block-scalar variants (`>`, `|`, `>-`, `|-`) surfaced a case where a description's raw text happened to start with a literal `"` character — `_common.py` parsed it correctly (the quote is content, not syntax, inside a block scalar), but `run_skills_ref`'s stripped-copy rebuild used naive `f"{k}: {v}"` interpolation, and writing that value straight onto a `description:` line produced ambiguous YAML that `skills-ref` rejected, failing a genuinely valid skill. Fixed by wrapping every reconstructed value in `json.dumps()` — YAML's double-quoted flow scalar is a superset of JSON string syntax, so this escapes any character that could break the line unconditionally, not as a special case. Verified: all four block-scalar variants now validate clean; full regression sweep unchanged.
- **`scripts/eval_loop.py`'s `runs_per_configuration` metadata didn't reflect actual data.** Found while running the audit regression-benchmarking workflow end-to-end for the first time (`drafting-changelog-entries`' old vs. new `SKILL.md`, one real run per eval per configuration via live subagents, graded by hand per the note above, then aggregated): the generated `benchmark.md` claimed "3 runs each per configuration" regardless of how many runs actually happened, since `generate_benchmark()` hardcoded `3` as a fallback whenever `--preset` wasn't passed. Added `observed_runs_per_configuration()`, which derives the count from the real per-(eval, configuration) run tallies in the loaded `grading.json` results instead of assuming it. Verified against both the real 1-run-per-config workspace and a synthetic 3-run-per-config workspace — reports the correct count in both directions. The regression-benchmark run itself confirmed the actual point of the exercise: **zero pass-rate delta** between `drafting-changelog-entries`' pre- and post-Lifecycle-section versions (33.3% both configurations, `eval_loop.py`'s own aggregation), i.e. adding the Lifecycle section didn't regress task performance.

## [2.0.0] - 2026-08-16

Stages 5-6 of the master spec, per the companion build prompt (Prompt B; kept locally rather than in this repo, matching Prompt A's precedent). Read the actual v1 code and the `[1.0.1]` dogfooding entry before designing Stage 6's audit heuristics, per the master spec's own instruction — `scripts/audit.py` reuses `validate.py` and `security_scan.py`'s functions directly rather than re-deriving equivalent checks, and never treats gitleaks/pattern-check absence as a hard error the way `[1.0.1]`'s fix treated silent test collisions as unacceptable: unavailable tooling reports `MANUAL`, not a false PASS or a crash.

### Added
- **Lifecycle framing** (`references/lifecycle.md`, row 14): capability-uplift vs. encoded-preference classification, a scored 0-10 timelessness threshold (≥7 durable), re-benchmarking triggers tied to model upgrades, and a "last verified against model X" convention. `creating-skills/SKILL.md` classifies itself as a working example — encoded-preference, timelessness 9/10, last verified against claude-sonnet-5 (2026-08) — in a new "Lifecycle" section, not just in the reference file.
- **Audit mode** (`scripts/audit.py`, rows 31-32): a `report` subcommand that runs a 21-item checklist pass against an existing skill (frontmatter validity, security-scan cleanliness, evals presence, body-size limits, reference depth/TOC, content hygiene, lifecycle classification, and a heuristic degrees-of-freedom proxy — each PASS/FAIL/WARN, plus four items marked `MANUAL` where no pattern can substitute for a human/LLM read: coherent-unit scoping, multi-model testing, description-optimizer usage, and inline-vs-fork correctness); an upgrade-vs-rebuild decision gate that defaults to upgrade-in-place and only recommends rebuild for a named condition (frontmatter and description both failing together, a capability-uplift skill under the 7/10 timelessness bar, or body size more than double the limit); an institutional-knowledge safeguard that flags `##` section headings with no obvious checklist counterpart for an explicit keep/fold-in/discard decision, never a silent drop; a `bulk` subcommand that runs the same report across every skill found under a directory and prints a collective table (reuses `_common.find_skill_dirs`, promoted out of `dedup_search.py` so both scripts share one implementation rather than two copies); and an optional `pr-plan` subcommand (row 32, lower priority than the rest) that prints an additive-only-changes contribution plan for a third-party skill without ever calling `gh` itself. Regression benchmarking (item 4) is documented as an `eval_loop.py` before/after workflow in `SKILL.md`'s new "Auditing existing skills" section rather than reimplemented — the same division of labor the eval engine already uses, since a standalone script can't spawn the subagents that actually run it.
- **Verified against a real third-party skill, not just a stub.** `audit.py report` was run against Anthropic's actual shipped `skill-creator` (`~/.claude/plugins/marketplaces/claude-plugins-official/plugins/skill-creator/skills/skill-creator` on the machine this was built on) — confirmed a checklist pass rate consistent with the master spec's own Confidence Notes (no frontmatter validation, no security scan, no lifecycle classification, evals present but no gerund-form naming), decision `upgrade-in-place` (its gaps are structural additions, not a broken triggering-logic rebuild case), and real institutional-knowledge candidates surfaced from its actual section headings ("Communicating with the user," "Report structure," "Advanced: Blind comparison," among others). `audit.py bulk` was run against three dummy skills of deliberately varying quality (a clean encoded-preference skill with evals, a mediocre skill with Windows paths and unexplained bare directives, and a broken skill with a name/directory mismatch and no usable description) and produced the expected spread: two `upgrade-in-place`, one `rebuild` — confirming the decision gate's named conditions actually discriminate rather than defaulting to one branch regardless of input. Both dummy fixtures and their location were scratch material for this verification pass, not shipped as part of the plugin.
- **Full Synthesized Checklist walkthrough**, now unrestricted by the v1/v2 exclusions the master spec scoped out at the v1 release checkpoint — every item checked against the complete v1+v2 repo and its file(s) named directly (no separate tracking document; the checklist itself lives in the master spec, not duplicated here).

### Changed
- `scripts/dedup_search.py`'s `find_skill_dirs` moved to `scripts/_common.py` (`audit.py bulk` needed the identical directory-discovery logic; the `scripts/`-discipline rule this plugin already enforces on authored skills — one implementation, not two copies that drift — applies to its own `scripts/` directory too).
- `README.md`'s release-scope section and comparison table updated to reflect v2 as shipped rather than planned.

## [1.0.1] - 2026-08-16

### Fixed
- **`scripts/description_optimizer.py`: trigger-eval self-collision when testing description changes for an already-installed skill.** Found while dogfooding v1 on a real project skill (`drafting-changelog-entries`, added to this repo's own `.claude/skills/` as the v1 dogfood exercise — not part of the shipped plugin). The per-query synthetic test copy gets a randomized name specifically so it won't collide with anything real, but if the skill under test is *also* sitting at its real, natural name in the same project with a near-identical description, the model tends to reach for the naturally-named real one instead of the synthetic candidate — and the harness only counts a trigger against the synthetic name, so every one of those turns silently reads as a miss. Confirmed directly: the exact same query/description pair scored 0/3 with the real skill present, 1/3 with it hidden. `run_eval` now moves the real `.claude/skills/<name>/` aside for the duration of the run and restores it afterward (`try`/`finally`). Verified the restore fires on normal completion; the crash-safety property for an abnormal exit mid-run rests on the `try`/`finally` construct itself rather than on having reproduced an actual kill during testing — worth a closer look before relying on it for anything long-running. Only matters for improving an existing skill — a brand-new skill has nothing installed yet to collide with.

## [1.0.0] - 2026-08-15

Stages 1-4 of the master spec, built and verified against a live `claude -p` session and a real `gitleaks` install (not just documentation) — per the companion build prompt (Prompt A; kept locally rather than in this repo, not published alongside the plugin).

### Added
- **Eval engine**, ported from `skill-creator` with no loss of capability: parallel with/without-skill subagent runs from a clean context, `agents/grader.md`/`comparator.md`/`analyzer.md` subagent roles, the `evals/evals.json` test-case format, benchmark aggregation with mean/stddev/delta (`scripts/eval_loop.py`), an analyst pass flagging always-pass/always-fail assertions, blind A/B comparison, the HTML eval-viewer (`eval-viewer/generate_review.py` + `viewer.html`, Outputs/Benchmark tabs, `--static` mode, `--previous-workspace` diffing), and the trigger-eval review template (`assets/eval_review.html`).
- **Description optimizer** (`scripts/description_optimizer.py`): 60/40 train/validation split (shuffled once, fixed across iterations), 3x runs per query against a 0.5 trigger-rate threshold, up to 5 iterations, selection by validation pass rate. Fixed two real bugs found while verifying this against a live session: the trigger-registration path (`.claude/skills/<name>/SKILL.md`, not `.claude/commands/` — the latter registers as a slash command and never appears in `available_skills`) and a concurrency race between simultaneously-launched `claude -p` subprocesses sharing one project root (fixed with a small launch stagger).
