# Changelog

All notable changes to SkillArtisan are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [Semantic Versioning](https://semver.org/), interpreted for this project as:

- **Major version bump (1.0.0 → 2.0.0)** marks a v-stage boundary, not just a breaking change — v1 → v2 is the deliberate release split (see the master spec's "Build Stages → Plugin Files → Release Scope"), not an accident of semver discipline.
- **Minor version** for new capability within a stage that doesn't break existing usage (e.g. adding cross-agent evaluation as an opt-in mode within v1).
- **Patch version** for fixes — corrected patterns, tightened validation, documentation accuracy.

## [2.5.7] - 2026-08-20

### Fixed
- **`check_path_references`' sixth false-positive mechanism, the first to be repaired rather than skipped**: `trailofbits/skills` uses a `{baseDir}`-prefixed template-variable convention (`{baseDir}/references/quick-reference.md`) for cross-skill-relative links — a real, cross-platform convention (not Claude Code's own `${CLAUDE_SKILL_DIR}` syntax), verified exhaustively (41 of 41 instances across 7 skills resolve to real files once the prefix is stripped, not sampled). Unlike the existing `SKIP_PREFIXES` entries (`http://`, `https://`, `mailto:`, `#`, `~` — none locally verifiable), `{baseDir}` references are real and checkable, so the fix strips the prefix and re-checks existence rather than skipping validation outright — a genuinely broken `{baseDir}/nonexistent.md` reference is still correctly caught. Regression tests added to `tests/test_validate.py` covering both directions.

### Notes
- Phase 11 of the real-world audit pilot: 197 skills audited across `nomadamas/k-skill` (the pilot's first non-English corpus, Korean) and `trailofbits/skills` (a named professional security-research firm, CC-BY-SA-4.0 licensed — audited under an "audit yes, adapt no" policy). Found and documented (not code-fixed, by design) a genuine, two-dimensional English-bias bug in `description-pushy-imperative` — a literal-English-phrase regex and a length threshold calibrated for English text density, both confirmed against real Korean descriptions, FAILing/WARNing 77% of the corpus. Tracked as [#10](https://github.com/EONRaider/SkillArtisan/issues/10), left for a deliberate design decision rather than a speculative regex guess. Full narrative: `skill-artisan/benchmark/audit-pilot/RESULTS.md`'s Phase 11 section.

## [2.5.3] - 2026-08-20

### Fixed
- **The test suite's `REPO_ROOT = parents[2]` convention broke ~15 tests when run from an installed plugin copy**, not just the dev checkout — flagged, but deliberately left unfixed, at the end of the prior live-install check. Every test file computed `SCRIPTS_DIR = REPO_ROOT / "skill-artisan" / "scripts"` assuming a full monorepo layout (`<monorepo-root>/skill-artisan/tests/test_x.py`, two parents up is the monorepo root); `EONRaider/claude-plugins`' `git-subdir` source (`path: "skill-artisan"`) fetches only that directory's contents, so in an install the same test file sits one level shallower and the re-appended `"skill-artisan"` segment resolves nowhere. New shared `tests/_repo_paths.py` computes `PLUGIN_ROOT` as the test file's grandparent directory directly — always correct in both contexts, since that's exactly what `git-subdir`'s `path` fetches — and detects `MONOREPO_ROOT` (`None` in an install) for the handful of files genuinely outside the plugin (`action.yml`, the monorepo's own root `README.md`, the pre-2.5.1 root `marketplace.json`), which now `self.skipTest(...)` with a stated reason instead of erroring when those don't exist. All 15 affected test files updated to import from it. Verified three ways, not just by inspection: full suite from the dev checkout (121 pass), from a constructed installed-copy layout (116 pass, 5 skip with named reasons), and — the real test — copied into the actual `~/.claude/plugins/cache/eonraider/skillartisan/2.5.2/` directory `claude plugin install` had populated from the live marketplace and run from there (same 116/5 split).

## [2.5.0] - 2026-08-20

### Added
- **`audit.py` now understands skill provenance** — resolving [#4](https://github.com/EONRaider/SkillArtisan/issues/4), the architectural parent of the audit pilot's deferred gaps. Three checklist items (`evals-present`, `security-scan-marker-current`, `lifecycle-classified`) verify artifacts only this plugin's own pipeline produces, and FAILed on effectively 100% of the 1,418 third-party skills audited across all six pilot corpora regardless of actual quality — `RESULTS.md`'s stated cost was that an outside author "would reasonably conclude the tool doesn't understand their skill wasn't authored for it." `report` and `bulk` now take `--source {auto,first-party,third-party}` (default `auto`), and in third-party mode those three items report a new fifth status, **`N/A`** — the detail still says what was observed (and what adopting the skill into the pipeline would add), but the item is excluded from the pass-rate denominator alongside WARN/MANUAL. Detection is deliberately "ANY pipeline artifact present → first-party" rather than requiring all three: requiring all would make the checks unfalsifiable, since a fresh first-party draft missing an artifact would silently reclassify as third-party and skip the exact gate those items enforce — `--source first-party` is the documented override for artifact-less drafts. Detection also demands *this pipeline's* marker shape (JSON with a content hash), because end-to-end verification against the vendored daymade clone found 85 skills shipping a same-named plain-text `.security-scan-passed` from a different tool, which existence-only detection misclassified — caught before commit precisely because verification ran against real corpora, not just fixtures. Verified effect: daymade's `competitors-analysis` goes from 12/16 (75%) with 3 artifact FAILs to 12/13 (92%) with 3 informative N/A lines; a bulk run over `obra/superpowers` resolves source per skill in one pass. `pr-plan`, which builds contribution plans from FAIL items only, automatically stops proposing SkillArtisan-pipeline artifacts to upstream maintainers — a correctness fix it inherited for free. New fixture `tests/fixtures/third-party-fixture/` and regression tests in `tests/test_third_party_mode.py`; the pilot-era `KNOWN_BOILERPLATE_IDS` stopgap in `aggregate_findings.py` is left as-is (historical pilot tooling, its comment already points here).
- **`validate.py` now recognizes known third-party metadata field families** — resolving [#7](https://github.com/EONRaider/SkillArtisan/issues/7). mukul975/Anthropic-Cybersecurity-Skills' consistent framework-mapping taxonomy (`mitre_attack`, `nist_csf`, `domain`, `subdomain`, `author`, `tags`, `version`, plus per-skill `d3fend_techniques`/`mitre_f3`/`atlas_techniques`/`nist_ai_rmf`) hard-FAILed `frontmatter-valid` on **817 of 817** skills — a real, coherent taxonomy, not sloppy authoring, and exactly the "general answer rather than field-by-field allowlisting" the pilot notes called for. `THIRD_PARTY_FIELD_FAMILIES` maps family names (`security-framework-taxonomy`, `common-authoring-metadata`) to their fields; `classify_extended_fields` gained a third bucket, and family fields now produce a portability *warning* (naming the family and recommending `metadata:` nesting for spec compliance) instead of an error. Deliberately NOT admitted, so they keep hard-erroring: the recorded true positives and bespoke one-off conventions from Phases 5-6 — `user_invocable` (underscore typo for the real `user-invocable`), `triggers`, `command`, `agents`, `compatible_tools`. Knock-on effect, intended and verified: `audit.py`'s `frontmatter-valid` item reads only validation errors, so those 817 skills flip FAIL→PASS on it with no audit-side change. Regression tests in `tests/test_field_classification.py`, including a guard that the new warning text can never collide with the substring `audit.py` uses to bucket the naming-convention warning.

### Deferred, not forgotten
- All four `audit-gap` issues from the audit pilot are now closed (#5/#6 in `[2.4.12]`, #4/#7 here) — the label's tracking job is done. One residue observation recorded for honesty, not action: pilot-era audit runs wrote this pipeline's own scan markers into some gitignored vendored clones (e.g. obra's `brainstorming`), so auto-detection classifies those specific local copies as first-party; that's the detector working as specified on residue our own tooling left, `--source third-party` covers it, and historical pilot artifacts stay untouched by convention.

## [2.4.12] - 2026-08-20

### Fixed
- **`validate.py`'s Claude Code field allowlist was missing eight officially documented frontmatter fields** — resolving [#5](https://github.com/EONRaider/SkillArtisan/issues/5), which had been deliberately deferred pending confirmation that `agent:` is a real Claude Code field rather than a bespoke author convention. It is real: the official frontmatter reference (https://code.claude.com/docs/en/skills.md) documents `agent` as "which subagent type to use when `context: fork` is set" — exactly the usage found in daymade's `competitors-analysis`, the corpus skill that exposed the gap. The same check against the docs showed `CLAUDE_CODE_ONLY_FIELDS` was also missing `arguments`, `disallowed-tools`, `model`, `effort`, `background`, `hooks`, and `shell`, so the fix synced the whole allowlist rather than adding one field. `competitors-analysis` now validates clean (verified against the vendored clone), while Phase 5's recorded true positive — `user_invocable`, an underscore typo for the real `user-invocable` — still hard-errors, pinned in both directions by `tests/test_field_classification.py`. `references/surface-matrix.md`'s Claude Code field table updated to match, keeping its "documents these in full" claim true.
- **`audit.py`'s `description-pushy-imperative` check only recognized the literal substring "use when"** — resolving [#6](https://github.com/EONRaider/SkillArtisan/issues/6), the most heavily corroborated of the four deferred gaps: five independent corpora measured equivalent-but-differently-phrased trigger framing ("use whenever", "use for X, Y, Z", "use during authorized red-team...", "use this skill when...") at incidence rates of ~40% sampled (daymade), 82% (mukul975, 668/817), 55% (glebis), and 8.6% (alirezarezvani, 30/349). The original deferral wanted trigger-accuracy data proving the phrasings perform differently before broadening; no such evidence surfaced across 1,418 skills, and the volume of legitimate skills WARNed for pure phrasing variance settled the call. The match is now a bounded regex (`use [this skill] when/whenever/if/for/during`) rather than an anything-goes loosening — a bare "use" or an obra-style "you MUST use this" with no trigger clause still WARNs, because pushy without saying *when* doesn't inform the trigger decision, and the ≥100-char length gate is unchanged. Also fixed the check's OR-phrased WARN message (flagged in `RESULTS.md` from Phase 7): it now says *which* condition fired — missing framing, under 100 chars, or both — instead of leaving an author like obra's `test-driven-development` ("Use when" present, 72 chars) to guess. Regression tests: `tests/test_description_framing.py`.

### Deferred, not forgotten
- [#4](https://github.com/EONRaider/SkillArtisan/issues/4) (third-party-source mode) and [#7](https://github.com/EONRaider/SkillArtisan/issues/7) (framework-mapping field family) are the next release's scope — designed together, since #7's "known third-party metadata" concept is the validate.py half of #4's third-party awareness.

- **`description_optimizer.py`'s train/validation split gave no warning when the validation set was too small to be a meaningful generalization check.** `split_eval_set()` computes a single train/validation split once, with a hardcoded `seed=42`, before any iteration runs; `improve_description()` is then deliberately never shown which validation queries are failing (`blinded_history` strips every `test_`-prefixed key — correct anti-overfitting design). But for a small eval corpus, the one-time holdout can be tiny: on a real corpus skill (`bilibili-source`, 9 should-trigger examples, the tool's own default `holdout=0.4`), the validation split held exactly 3 should-trigger examples — and those 3 specific queries failed identically across all 5 iterations, completely unmoved by materially different description rewrites, because the optimizer had zero visibility into them from iteration 1 onward and the split never rotates. With this few validation examples per class, a single query flipping swings the reported score by 20+ percentage points, and nothing in the tool surfaced this — a user just saw `best_test_score: 3/6` with no indication the run was structurally incapable of doing better. Added `split_validation_warning()`: prints a `WARNING:` to stderr when either validation class has fewer than 5 examples, and surfaces the same message in the returned dict's new `validation_warning` key and in the HTML report's summary panel, so it's visible whether a caller is watching stderr, reading the JSON, or just the report.
- **Confirmed present, unfixed, in `skill-creator`'s own current `run_loop.py`** — identical `split_eval_set()` (same fixed `seed=42`, same `max(1, int(len(trigger) * holdout))` logic, same default `holdout=0.4`), and the identical blinding mechanism, down to the same code comment ("Strip test scores from history so improvement model can't see them", line 194). ## [2.2.3] - 2026-08-18

A fourth real bug found in row 15's ported eval engine, this time by deliberate hardening rather than incidental discovery during a benchmark run — triggered by investigating why Axis 2 trigger-accuracy scoring (`axis2_trigger_scorer.py`) had `--num-workers` capped at 1.

### Fixed
- **`description_optimizer.py`'s `run_single_query()` published and tore down its synthetic per-query skill directory non-atomically** (`mkdir()` then a separate `write_text()` to publish; `unlink()` then a separate `rmdir()` to tear down), both against the same shared `.claude/skills/` directory every concurrent worker scans at startup. Between the two calls in each pair there's a real window where a concurrent scan can observe a broken entry — a directory with no `SKILL.md` yet, or (for teardown) one that's already been emptied but not yet removed. Fixed by building each entry in a hidden staging directory and publishing/removing it with a single `os.rename()`, which is atomic on the same filesystem: a directory listing during either operation now only ever sees the complete entry or nothing, never a partial one. Verified with a dedicated concurrency stress test (no LLM calls — pure filesystem race, `race_stress_test.py` under scratch) that reproduces the mechanism directly: with a deliberate delay forced into the vulnerable window, the old code exposed a broken entry in ~99% of concurrent scans; the fix brought that to 0%.
- **Correction to prior understanding, not a fix**: this atomic-write race is real and worth fixing, but it turned out not to be the (or the whole) cause of the `--num-workers 4` → 0% trigger-detection collapse originally documented in `axis2_trigger_scorer.py`'s `--num-workers` help text. Live validation after the fix (`debugging-network-issues`, `--num-workers 4` vs. the known-good `--num-workers 1` baseline of 14/16) still dropped to 10/16, with every failure showing 0 triggers across all runs and the log showing every query timing out at 180s — including ones that "passed" only because a timeout reads as not-triggered, which happens to match a should-not-trigger query's correct answer. Sequential runs show the same 100%-timed-out log pattern but sane, varied pass rates, because `run_single_query` correctly latches its `triggered` result from a mid-stream tool-use event well before the session's later work (actually reading/using the skill) blows through the timeout — that part is normal. What's different at 4 workers is that several queries never got that far at all: the tool-call decision itself didn't happen in time. That points to raw resource contention (four concurrent `claude -p` processes competing for CPU/network/API throughput on one machine) as the dominant remaining bottleneck, not a filesystem race — so `--num-workers 1` stays the safe default until that's separately investigated. The fix above is real and shipped regardless; it just isn't the unlock it looked like it might be.
- **Confirmed present in `skill-creator`'s own shipped `run_eval.py`, and worse**: the identical `mkdir()`-then-`write_text()` pattern exists there too (lines 57/68), with more code running between the two calls than SkillArtisan's version had even before this fix — a wider vulnerable window, still unfixed upstream as of this check. See the master spec's Confidence Notes for the running tally of verified skill-creator defects.
