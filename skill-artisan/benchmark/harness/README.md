# Cross-arm orchestration harness

Drives all 5 comparison arms through the same starting draft (`corpus/<skill>/seed.md`)
per corpus skill, per the master spec's "Methodology per run," step (1). This is the
single biggest engineering piece in the Best-in-Market Scorecard plan.

## Division of labor (same precedent as `scripts/eval_loop.py`)

`run_authoring.py` manages workspace state (creates the per-run directory, writes the
prompt, tracks pending/running/complete/failed) but does **not** spawn the authoring
subagents itself — a standalone script can't invoke the Task/Agent tool. That orchestration
is the chat session's job: for each `(corpus-skill, arm)` pair, spawn an Agent-tool
subagent with the prompt `run_authoring.py init` already wrote to `prompt.md`, then record
the result with `mark-complete`/`mark-failed`.

## Invocation mechanism

All 4 authoring arms (`skill-creator`, `daymade-fork`, `skillforge`, `creating-skills`)
are invoked the **same way**, uniformly, rather than giving the two natively-installed
arms (`skill-creator`, and `creating-skills` if this session has it installed) a native
`Skill`/`Task(subagent_type: ...)` invocation while the two vendored arms get a simulated
one. Fairness requires one mechanism for all four: a general-purpose subagent is told to
read the arm's `SKILL.md` (and one level of its own references, the same reference-depth
convention `creating-skills` itself documents) and follow that process exactly, given the
corpus skill's `seed.md` as the task, producing a real skill directory at a fixed output
path. See `PROMPT_TEMPLATE` in `run_authoring.py`.

## Open design question this needs your input on before any real run

**Nested subagent spawning is unconfirmed.** Three of the four authoring arms'
own documented processes (`skill-creator`, `daymade-fork`, `creating-skills` all
explicitly call for spawning *their own* with-skill/without-skill/grading subagents as
part of testing and description optimization — SkillForge's RED/GREEN gate needs the
same thing). Whether a Task-tool-spawned subagent can itself spawn further subagents in
this environment has not been tested. If it can't, each arm's authoring subagent will
hit a wall partway through its own documented process and can only produce a first-pass
draft (frontmatter + body + structure), not the fully eval-loop-optimized skill each
arm's process is actually designed to produce — which would understate every authoring
arm's real quality, not just one of them evenly, so it doesn't bias the comparison, but
it does mean Axis 1/2 scores would reflect "first-draft quality" rather than "quality
after each arm's own full iteration loop."

## Workspace layout

```
benchmark/harness/workspace/<corpus-skill>/<arm>/
    seed.md         # copy of corpus/<corpus-skill>/seed.md
    prompt.md        # exact prompt given to the authoring subagent
    output/          # subagent writes the resulting skill directory here
    status.json      # {state, corpus_skill, arm, created_at, completed_at,
                      #  total_tokens, duration_ms}
```

`workspace/` is gitignored scratch output, not committed — regenerated by re-running the
harness, same as any other eval-engine workspace in this project.

## Commands

```bash
python run_authoring.py init <corpus-skill> <arm> [--workspace DIR]
python run_authoring.py init-all [--corpus-skills a,b,c] [--workspace DIR]
python run_authoring.py mark-complete <corpus-skill> <arm> [--total-tokens N] [--duration-ms N]
python run_authoring.py mark-failed <corpus-skill> <arm> --reason TEXT
python run_authoring.py status [--workspace DIR]
python run_authoring.py cost [--workspace DIR]
python arms.py   # validates all 4 authoring entry points still exist on disk
```

## Cost tracking (`cost` subcommand)

Sums actual tokens spent so far — exact, from completed runs' recorded `total_tokens` —
and projects a rough remaining cost using each arm's own average where available (falling
back to the overall average for an arm with no completed runs yet). **Advisory only**: no
tool in this environment reports remaining session quota, so this cannot tell you whether
the next spawn will actually fit — the only signal for that is reactive, a spawn failing
with a session-limit error that happens to include a reset timestamp. What this *does* give
is real, exact spend-so-far and an increasingly accurate per-arm forecast as more runs
complete, which is what actually informs pacing/concurrency decisions.

## Status

The nested-subagent question above resolved (subagents can spawn their own children, but
completion notifications route to the top level, not back to the spawning parent — see
Operational gotchas below). The original 5-arm comparative plan was piloted on 3 skills,
hit real cost/reliability limits (see the master spec's dated correction at the top of
"Best-in-Market Scorecard"), and was redirected to single-arm regression/QA testing of
`creating-skills` alone. That's what actually ran:

- **Authoring (Step 1): done.** All 25 tracked runs (12 pilot + 13 more, `creating-skills`
  arm) show `complete` via `run_authoring.py status`. Total authoring spend: ~7.26M tokens
  initial + ~2.9M tokens retesting 6 runs whose eval loops were interrupted mid-session —
  ~10.1M tokens total. Each run got a full with-skill/baseline eval loop, grading, and
  aggregation; results live under `workspace/<skill>/creating-skills/`.
- **Axis 2 trigger accuracy (Step 2): done.** All 16 corpus skills scored single-arm,
  sequential (`--num-workers 1` — see gotchas), via `axis2_trigger_scorer.py` /
  `run_axis2_full_sweep.sh`. Results in `axis2-results/<skill>__creating-skills.json`.
  9 of 16 skills scored poorly on should-trigger rate (0-22%) at the original
  `--runs-per-query 1`. A 3-skill diagnostic pilot at `--runs-per-query 3`
  (`run_axis2_pilot_3x.sh`, results in `axis2-results/pilot-3x/`) found the picture was
  mixed, not uniformly a real problem — see Findings below. The remaining 6 of the 9
  (`dataset-bias-auditor`, `deep-research`, `excel-automation`, `narrative-arc-builder`,
  `repomix-unmixer`, `structured-data-diff`) were never re-verified at 3x and should be
  treated as unconfirmed, not as established real problems.
- **Task-success (Step 3): minimal pass done, mostly open.** Given no clean token-cost
  estimate exists for the eval-loop-only cost (only authoring cost is tracked, via `cost`

  full 28-run plan: retest just `deep-research`'s eval-3, which had regressed to -15% vs.
  baseline. Confirmed real and fixed (see Findings). The 3 skills with zero task-success
  data (`auto-repo-setup`, `design-style-picker`, `narrative-arc-builder`) remain open —

## Operational gotchas learned the hard way

- **Nested subagent completion notifications route to the top-level session, not back to
  the spawning parent subagent.** A parent that spawns child executors/graders and "waits
  for their notifications" will wait forever unless the top-level session relays completion
  back to it explicitly via `SendMessage`. Always check `ListAgents` + file timestamps on
  disk before trusting a parent's self-reported "still waiting" status.
- **2 parent subagents in flight at a time** has been the safe, established concurrency
  convention for this Agent-tool-based orchestration (distinct from the `claude -p`
  subprocess concurrency issue below).
- **`claude -p` subprocess concurrency above 1 worker is unsafe for two independent
  reasons**, confirmed separately: (1) resource contention — concurrent processes on one
  machine slow each other down enough that the tool-call decision itself can miss the
  timeout window (confirmed live at `--num-workers 4`: a 14/16 baseline dropped to 10/16,
  unrelated to (2)); (2) a filesystem race in `description_optimizer.py`'s synthetic
  skill-directory publish/teardown, fixed in `2.2.3` but not sufficient on its own to fix
  (1). Always `--num-workers 1` for `axis2_trigger_scorer.py` until (1) is separately
  investigated.
- **Task-success and trigger-accuracy are different axes for a reason — don't let one
  eval run answer both.** A task-success ("with-skill") run should deliberately hand the
  skill to the executor rather than relying on organic triggering; conflating the two
  produces a run that silently tests nothing (a skill with a low trigger rate just won't
  fire on its own, and you'll grade the model's general ability instead of the skill).
  Learned the hard way on the `deep-research` retest's first attempt.
- **Don't directly edit a file a still-running background agent is actively writing to,
  even to help it along** — a direct edit can race with the agent's own writes and
  silently revert some of its concurrent progress. Relay information via `SendMessage`
  and let the agent make its own edits instead.
- **Eval-workspace directory naming is non-uniform per-skill** (`eval-workspace/iteration-1/`
  vs `creating-skills/eval-workspace/iteration-1/` vs
  `creating-skills/output/eval-workspace/iteration-1/` vs `_bench/` — each authoring agent
  chose its own convention). Don't hardcode a path pattern when checking for
  `grading.json`/activity across multiple skills — search the whole skill's workspace tree.
- **A background monitor script checking file activity by a fixed subpath can produce
  false "stalled" alarms** — always re-verify against the actual filesystem (broad `find`)
  and `ListAgents` before concluding something is actually stuck, not just proxied wrong.
- **Fixture repos for git-related skill testing should stay under the scratchpad or
  workspace, not a general home-directory location** — verify and clean these up after
  retests involving real git repos.
